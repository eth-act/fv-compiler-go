# Nightly gate

The per-PR checks (AGENTS.md) build the affected modules and run parity on the quick corpus.
The nightly gate checks the whole of the newest `origin/main` against the full corpus every
night: `scripts/nightly-gate.sh`, run by a systemd `--user` timer. Results go to the
**Nightly gate** status issue (label `nightly-gate`), one comment per night.

## Steps

The gate runs in its own detached worktree, `../fv-compiler-go-wt/nightly-gate`. Each run
checks out `origin/main` there after a fetch, and then runs the steps from that commit's copy
of the script. The full corpus is the version that `../gofv-corpus/<pin12>/full` points to
when the run starts (`readlink -f`), so a corpus switch during the run does not affect it.

| step | command | red when |
| --- | --- | --- |
| `build` | `lake build GoFV GoFVTest gofv-ssa-opt pass-parity ssa-check` | any module or executable fails |
| `allproof` | `scripts/gen-allproof.sh` if `--check` says the file is stale, then `lake build GoFVTest.Proof.AllProof` | two proof modules declare the same name |
| `no-sorry` | `scripts/no-sorry.py` | `sorry` or `admit` appears in a tracked `.lean` file, outside comments and strings |
| `reverts` | `scripts/scan-history-reverts.sh 80` | a recent squash merge deleted a file added by one of the 8 commits before it, or set a file back to its state before the previous commit that touched it (#191 undid #190); acknowledge a known incident in `scripts/reverts-ack.txt` with its restore issue, or an intended revert (`check-reverts.sh --allow`) with its PR |
| `axioms` | `scripts/axioms-audit.sh --replay` | a constant of `GoFV` or `GoFVTest` depends on any axiom other than `propext`, `Classical.choice`, `Quot.sound` and the `_native` axioms listed in `scripts/axioms-allowlist.txt`, an `@[implemented_by]`/`@[extern]`/`@[export]` declaration is not listed there, or the kernel rejects one of their constants on replay |
| `ssa-check` | `ssa-check <full corpus>` | a section is not well formed (`GoFV.SSA.check`) |
| `parity` | `scripts/parity.sh <full corpus>` | a registered pass mismatches the stock pass, or reports an error |
| `check` | `gofv-ssa-opt --check --jobs 4 <full corpus>` | the whole pipeline diverges from stock, or a Lean pass fails (docs/DRIVER.md) |
| `e2e` | driver toolchain, then `scripts/driver-e2e.sh --mode full` | a std archive or a binary differs from stock, a program's output differs, or a function falls back to the stock passes |
| `verified` (report) | `gofv-ssa-opt --check --verified --jobs 4 <full corpus>` under `timeout $GATE_VERIFIED_TIMEOUT` (default 6h; 222 min on 2026-11-07 under load) | never: the verified pipeline's numbers (docs/DRIVER.md, "Verified mode") |
| `e2e-verified` (report) | `scripts/driver-e2e.sh --verified` with the toolchain of `e2e` | never: programs built with the verified pipeline, run against stock |

- `allproof`: every `GoFV/Proof` module must import together with every other (issue #133), so
  that any proof, and the axioms audit, can use all of them. `GoFVTest/Proof/AllProof.lean`
  imports them all; it is generated by `scripts/gen-allproof.sh`, which a PR that adds or
  removes a proof module reruns. Each module builds alone even when two of them declare the
  same name, so only this import notices. Fix a clash by moving a shared helper into a module
  both import (for example `GoFV/Proof/Witness/Util.lean`), or by making a local one `private`.
  `build` builds the committed file (it is in `GoFVTest`). If that file is stale, `allproof`
  regenerates it in the gate worktree first (its log says so), so a new module is covered
  either way.
- The axioms audit (`scripts/axioms-audit.sh`) decides with the compiled program `axioms-audit`
  (`GoFVTest/AxiomsAudit.lean`), so no code of an audited module runs while it decides: it
  imports the modules with `importModules` and never enables initializers (a `#eval` audit file
  ran every imported `initialize`, which could print a passing result and exit). It audits every
  constant, of every kind (theorems, definitions including `partial`/`unsafe` ones, opaques,
  axioms), declared in `GoFV/**` and `GoFVTest/**` (the executable roots, which define `main`,
  read one by one from their `.olean`s), with the traversal of Lean's `collectAxioms`, the
  function behind `#print axioms`. Not only `GoFV/Proof` (as until 2026-11-05): the `@[csimp]`
  lemmas in `GoFV/Opt` and `GoFV/SSA` (`rng_eq_rngFast`, `depB_eq_depBFast`, …) decide which code
  the compiled checkers run, and `GoFVTest` holds the driver. The verdict is the program's exit
  code, decided on `Name`s (a theorem name with a newline cannot split a report line). `sorryAx`,
  `Lean.trustCompiler` and declared axioms are always violations, also when unused. A deliberate
  `bv_decide`/`native_decide` use adds its `…._native.…` axiom names to
  `scripts/axioms-allowlist.txt` in the same PR (docs/PLAN.md §0); each entry must have the
  shape of one (an axiom named `…._native.(native_decide|bv_decide).ax_…`, declared in a library
  module, of type `_ = true`, `decide _ = true` for `native_decide`), and pins its
  statement together with every definition of `GoFV`/`GoFVTest` the statement reaches (`NAME PIN`,
  a SHA-256 of their structural serialization, names component by component: `toString` prints a
  look-alike `«a.b»` as `a.b`; the audit prints the pin when it does not match). The shape does
  not prove the tactic generated it: Lean records nothing that distinguishes a hand-written
  `axiom ….native_decide.ax_1 : decide False = true`. The allowlist is the trust boundary: the
  audit prints every allowlist line that differs from `origin/main`, and the pin makes a change
  of an entry's statement, or of a definition it names (`plF`, the pipeline), such a line. An `@[implemented_by]`, `@[extern]` or `@[export]`
  declaration (it replaces or exports compiled code, as a `@[csimp]` lemma does) is a violation
  unless the allowlist lists it with its argument (`implemented_by NAME TARGET PIN`, the
  target pinned the same way, `extern NAME`, `export NAME SYMBOL`); an entry that matches nothing is an error. Every module imported by an audited
  module or an executable root must be audited or part of Lean read from the toolchain's
  `lib/lean` (module names come from paths, so a path component with a dot, a space or a control
  character is refused), and every `lean_exe` and `lean_lib` of `lakefile.toml` must be audited.
  The audit refuses a build that is not up to date (`lake build --no-build GoFV GoFVTest`), and
  needs every `GoFV` module and every `GoFVTest` module without `main` to import together. A theorem
  that several modules declare (an equation lemma realized in each) has one copy in the imported
  environment; the audit follows every copy. `scripts/axioms-audit-selftest.sh`
  plants each of these cases as a module and checks that the audit fails on it.
- Kernel replay. A `.olean` holds whatever the elaborator added: `set_option debug.skipKernelTC
  true` with `addDecl` puts a proof of `False` there that no kernel checked, and reading
  declarations (the audit, `#print axioms`) cannot tell. `axioms-audit --replay` sends the
  constants of `GoFV`/`GoFVTest` to the kernel again, every copy of a theorem several modules
  declare included (the extra copies under fresh names); unsafe and partial constants are not
  replayed, as in `leanchecker` (a checked constant that uses one fails). Modules are replayed in
  parallel, `GOFV_REPLAY_JOBS` at a time (`scripts/axioms-audit.sh`: one per 4 GB of
  `FV_MEMCAP`, so 2 at the default 8G): each in its own task once the modules it imports are
  done, against the constants the kernel has accepted so far, to which the kernel's versions of
  its constants are then added. A module whose witness proofs the kernel evaluates
  (`GoFV.Proof.Witness.Lower*`) holds about 3 GB while it is replayed. The nightly run replays
  the whole tree (`--replay`, on `Init`/`Std`/`Lean` alone) at `FV_MEMCAP=16G` under
  `../gofv-heavy.lock`, 4 modules at a time. Measured on an orb (16 cores): 8.2 minutes and
  14.3 GB peak RSS; 2 at a time 14.4 minutes and 9.0 GB; one at a time 30.5 minutes and 6.5 GB.
  The longest import chain is 46 modules, and its replay takes about 4.2 minutes. Per PR,
  `--replay-changed` replays the modules that differ from the merge base with `origin/main` and
  every module importing one (their elaboration ran the changed code), on the other modules,
  which an earlier replay checked; the whole tree when `lakefile.toml`, `lean-toolchain` or
  `lake-manifest.json` changed. It runs after the rebase onto `origin/main`, right before the
  merge (what it trusts is main). A leaf proof module takes seconds; #525 (`GoFV.Opt.LowerCheck`
  and 10 proof modules, 73 modules with their importers) 6.9 minutes and 8.7 GB at the default 8G
  (4.1 minutes at 16G, 11.8 minutes one at a time). `lakefile.toml` must not mention
  `skipKernelTC`, and no module may be a symlink (its source could change with no diff under
  `GoFV`/`GoFVTest`). Trust rests on sources: a module whose elaboration does IO
  (`run_meta`/`include_str` reading a repository file outside `GoFV`/`GoFVTest`, the directory,
  the environment, the clock) is trusted as unchanged until the nightly replay. (Lean's
  `leanchecker GoFV GoFVTest` checks the same, but imports each module's dependencies anew in
  parallel tasks: killed at 6 GiB after 11 minutes.)
- The audit program and scripts, and the allowlist, are built from the PR they check: a change to
  `GoFVTest/AxiomsAudit.lean`, `scripts/axioms-audit*.sh` or `scripts/axioms-allowlist.txt` needs
  a reviewer's look as much as a new axiom does.
- `no-sorry` also catches files that no target builds. The axioms audit catches a `sorry` that
  is hidden from the text, for example one inside a macro.
- `e2e` rebuilds the driver toolchain (`GOFV_GO_DRIVER=1 scripts/build-go.sh` into the gate
  worktree's `tmp/go-driver`) only when `patches/go/*.patch` changed. A hash of the patches is
  stored in `tmp/go-driver/.gofv-patches`.
- If `build` fails, the steps that depend on it are skipped. Otherwise every step runs, even
  after a failure.
- The two report steps show `report` (or `report (exit N)`) in the table and their numbers in
  the details; they never make the night red and never open a `gate-red` issue.

## Results

A run writes to `<gate worktree>/tmp/gate/<date>T<time>/`: `summary.md`, one `<step>.log` per
step, and the step outputs (`parity.md`, `check.md`, `axioms/`, `e2e-full/`). The summary is
posted as a comment on **Nightly gate**: the verdict, the commit, the corpus version, a table
of steps with result and time, and the numbers of each step.

On a red night the gate opens an issue for the first failing step. The issue is titled
`Nightly gate red: <step>`, has the label `gate-red`, and contains the commit and the tail of
the step's log. If an issue for that step is already open, the gate comments on it instead.
Close the issue when the fix is merged. The next green night confirms the fix on the status
issue.

## Schedule and memory

- `gofv-nightly-gate.timer` fires at 02:00, 03:00, 04:00, 05:00 and 06:00 local time
  (`OnCalendar=*-*-* 02..06:00:00`).
- An attempt runs the gate only if the gate has not yet run that day
  (`../gofv-gate.state`, next to the checkouts) and `MemAvailable` (the "available" column of
  `free -g`) is at least 20G (`GATE_MIN_FREE_GB`).
- Otherwise the attempt exits, and the next hourly attempt tries again. If the 06:00 attempt
  still lacks the memory, it posts "skipped" on the status issue.
- `gofv-nightly-gate.service` runs in `gofvgate.slice` (`MemoryMax=18G`, no `MemoryHigh`) with
  `MemoryMax=8G` for the gate's own processes, including the qemu runs of the e2e programs.
  Every build and check step runs in its own `scripts/memcap.sh` scope in the same slice
  (`FV_SLICE`); the builds run at 16G under the heavy lock. The gate is kept out of the agents'
  `gofv.slice`: above that slice's `MemoryHigh` every process in it is throttled, which on
  2026-11-07 slowed `ssa-check` from 21 min to more than 5 h.
- `../gofv-gate.lock` (`flock`) keeps two runs from overlapping. The service's `TimeoutStartSec`
  is 14h (a whole run took 7 h 5 min on 2026-11-07 under load average ~170).

## Operating it

```
scripts/nightly-gate.sh --install       # gate worktree + ~/.config/systemd/user units, timer on
systemctl --user start gofv-nightly-gate.service   # run now, as the timer would (once a day)
scripts/nightly-gate.sh --now [--no-post] [--force] # run now from a shell; --no-post: no issue
                                        # comments, --force: no memory check
systemctl --user list-timers gofv-nightly-gate.timer
journalctl --user -u gofv-nightly-gate.service
```

The unit templates are in `scripts/systemd/`. `--install` fills in the gate worktree path and
installs `gofvgate.slice` (no dash: `gofv-gate.slice` would be a child of `gofv.slice`). It also copies `scripts/gofv.slice` if
`~/.config/systemd/user/gofv.slice` does not exist.
